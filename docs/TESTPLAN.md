# 测试方案：「今天吃什么」Bug Fix 验证

## 准备工作

- 两个浏览器（或一个普通窗口 + 一个无痕窗口）模拟不同用户
- 打开 Supabase SQL Editor 备用，方便查表验证
- 测试地址：https://xtcningran.github.io/what-to-eat/

---

## T1 — 一个人吃饭（名字 + 黑名单）

| 步骤 | 操作 | 预期结果 |
|------|------|----------|
| 1 | 首页点「一个人也能吃饭」 | 进入 step2，显示名字输入框和排除餐厅列表 |
| 2 | 输入名字「小王」，排除一家餐厅，点「开始选择」 | 直接跳答题页（不经过 room.html 等待页） |
| 3 | 答完题进结果页 | 结果页不显示被排除的餐厅 |
| 4 | 回首页 | 历史卡片显示「小王」的记录，日期正确 |

| 步骤 | 操作 | 预期结果 |
|------|------|----------|
| 1 | 浏览器 A 用名字「小王」完成一轮，记录餐厅 X | — |
| 2 | 浏览器 B（无痕）用名字「小李」完成一轮，记录餐厅 Y | — |
| 3 | 查看各自首页历史 | A 只显示餐厅 X，B 只显示餐厅 Y，互不干扰 |

```sql

FROM history

LIMIT 10;
```

## T4 — 多人投票：历史记录每人一条

| 步骤 | 操作 | 预期结果 |
|------|------|----------|
| 1 | 浏览器 A 创建房间（名字「小王」），浏览器 B 加入（名字「小李」） | — |

| 4 | SQL 验证 | 「小王」和「小李」各有一条记录，`restaurant_name` 均为最终选择，`date` 为今天 |

```sql
SELECT user_name, restaurant_name, date
FROM history
WHERE user_name IN ('小王', '小李')
ORDER BY created_at DESC;
```

## T6 — 房间数据即时清理

完成一轮投票主持人确认后，执行以下 SQL：

```sql
-- 全部应为空（房间数据已清理）
SELECT * FROM rooms        WHERE id = '替换为实际房间码';
SELECT * FROM participants WHERE room_id = '替换为实际房间码';
SELECT * FROM answers      WHERE room_id = '替换为实际房间码';

-- 应有记录（history 按 user_name 存储，不随房间删除）
SELECT user_name, restaurant_name, date FROM history WHERE user_name IN ('小王', '小李');
```

| 表 | 预期结果 |
|----|----------|
| rooms | 0 条 |
| participants | 0 条 |
| answers | 0 条 |
| history | 参与人数条，数据完整 |

## T8 — 答题重复提交

| 步骤 | 操作 | 预期结果 |
|------|------|----------|
| 1 | 答完题点「确定」提交 | 显示「已提交！」等待页 |

## 快速回归检查

完成以上专项测试后，走一遍基本流程确认无回归：

- [ ] 首页「发起今日投票」→ 创建房间 → 等待页正常显示房间码
- [ ] 首页「一个人也能吃饭」→ 填名字和黑名单 → 直接进答题页
- [ ] 首页输入房间码「加入」→ join.html → 答题页
- [ ] 多人同时答题，最后一人提交后自动跳结果页
- [ ] manage.html 餐厅增删改查正常
- [ ] 结果页按料理分类展示排名，各分类最多显示 2 家
